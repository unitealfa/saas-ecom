# CODEX — MISSION COMPLÈTE : MODULE 19 — GESTION DES FACTURES SAAS

## 0. MISSION

Développe et valide intégralement le Module 19 d'Aydra : Gestion des factures SaaS.

Le module doit produire des factures à partir des abonnements et échéances, appliquer les règles de facturation, calculer les montants, réserver les numéros, générer les PDF et conserver l'historique.

Je veux une solution réellement intégrée, avec backend, frontend, sécurité, audit et tests complets.

Ne te contente pas de créer des Controllers ou d'obtenir un build réussi.

EXIGENCE DE SIMPLICITÉ :

Même un développeur débutant doit pouvoir comprendre facilement le chemin d'une facture dans le code.

N'ajoute pas d'architecture inutile. Utilise des méthodes claires et des Services métier simples.

Conserve tous les contrôles financiers indispensables.

## 2. ARCHITECTURE SIMPLE

Respecte l'architecture centrale existante :

Route → Middleware → FormRequest → Controller → Service → Model → BDD.

Laravel, PHP, MySQL, Fortify, Spatie Permission, Activity Log, IDs numériques et UUID publics doivent suivre les conventions réellement installées.

Le Controller doit être simple.

Le Service doit montrer clairement les étapes métier :

1. Vérifier le propriétaire.
2. Vérifier l'abonnement.
3. Vérifier l'échéance.
4. Trouver la règle applicable.
5. Calculer les montants.
6. Préparer le document.
7. Réserver le numéro.
8. Générer le PDF.
9. Finaliser l'émission.
10. Enregistrer l'audit.

Les opérations SQL doivent respecter les transactions et verrous requis. La génération du PDF doit se faire hors transaction SQL longue.

Évite les classes et abstractions sans utilité réelle.

Réutilise les Services du Module 18.

Ne duplique pas la numérotation ni les calculs.

## 3. TABLES ET CONTRATS

Tables principales :

- `saas_invoices`
- `saas_invoice_lines`

Tables liées :

- `users`
- `plans`
- `subscriptions`
- `saas_billing_settings`
- `media`
- `saas_document_deliveries`
- `activity_log`

Les factures et les avoirs partagent les tables documentaires :

- `document_type = 1` : INVOICE.
- `document_type = 2` : CREDIT_NOTE.

Ce module traite les factures INVOICE.

Ne crée pas une table distincte pour les avoirs.

Respecte les FK simples et composites.

Une facture doit lier :

- Le vrai propriétaire.
- L'abonnement parent type 1.
- L'échéance type 2.
- La RULE applicable de type 2.
- Le compteur SEQUENCE de type 1.
- La période.
- La devise.
- Les snapshots.
- Les montants.
- Les lignes.

Les colonnes GENERATED STORED sont calculées par MySQL, pas par le navigateur.

N'expose pas les IDs internes dans les routes ou réponses publiques.

## 5. RÈGLES DE CRÉATION

Avant toute création :

- Vérifier l'existence du propriétaire.
- Vérifier l'abonnement.
- Vérifier que l'échéance appartient à cet abonnement.
- Vérifier que les trois appartiennent au même propriétaire.
- Vérifier la période.
- Vérifier la devise.
- Vérifier la règle de facturation applicable.
- Vérifier les paramètres fiscaux validés.
- Vérifier les identités nécessaires.
- Vérifier l'absence d'opération logique déjà traitée.

Aucun montant ou ID interne critique ne doit être accepté aveuglément depuis le navigateur.

La source de vérité appartient aux règles et données métier du serveur.

Utilise une clé d'opération stable `operation_key` dans l'espace de noms serveur documenté.

Si une opération est rejouée, retrouve le document déjà créé et vérifie sa cohérence.

## 6. CALCULS

Utilise les types décimaux exacts du projet.

Interdiction d'utiliser des floats pour les montants monétaires.

Respecte :

- Quantités valides.
- Prix HT valides.
- Remises autorisées.
- Taxes structurées et validées.
- Montant HT non négatif.
- Montant taxe non négatif.
- Total TTC = HT + taxes.
- Total du document = somme des lignes.
- Périodes `[period_starts_at, period_ends_at)` avec fin supérieure au début.
- Devise DZD au lancement selon le schéma.

Aucun taux fiscal ne doit être inventé.

Si la configuration fiscale indispensable manque, conserve un état approprié ou bloque l'émission avec un message précis, conformément au workflow existant.

Ne crée pas de fausses données NIF, NIS, RC ou d'identité.

## 7. SNAPSHOTS ET IMMUTABILITÉ

Respecte :

- `billing_rule_snapshot`
- `saas_identity_snapshot`
- `customer_identity_snapshot`
- Identité de la règle appliquée.
- Période.
- Lignes.
- Montants et taxes.
- Numéro de facture.

Après préparation figée, ne modifie plus les données documentaires comme si elles étaient un brouillon ordinaire.

Après ISSUED, le document est historique et immuable.

Un changement ultérieur de plan, de règle, de coordonnées ou d'identité ne doit pas modifier le PDF déjà émis.

Une correction doit passer par le Module 20 et les mécanismes documentés.

## 8. ÉMISSION ET PDF

Implémente le processus prévu par C8 :

1. Identifier `operation_key`.
2. Verrouiller les enregistrements nécessaires dans un ordre stable.
3. Valider tous les liens et montants.
4. Sélectionner et verrouiller le compteur.
5. Réserver le numéro une seule fois.
6. Figer la règle, les snapshots et les lignes.
7. Enregistrer PREPARING.
8. Terminer la transaction courte.
9. Générer le PDF privé.
10. Vérifier l'existence réelle du fichier.
11. Calculer et vérifier son empreinte.
12. Enregistrer le média.
13. Passer à ISSUED dans une transaction.
14. Enregistrer l'intention durable de transmission prévue par `saas_document_deliveries`.
15. Auditer l'opération.

Ne considère pas l'intention d'envoi comme un envoi réellement réussi.

La création d'une intention nécessite un canal et un destinataire utilisable, conformes au schéma. Ne crée pas de destinataire inventé pour contourner la contrainte.

Si les prérequis d'envoi sont absents, signale le blocage précisément au lieu de fabriquer une preuve d'envoi.

Le PDF doit contenir les informations fiscales effectivement validées, les lignes, la période, les montants, les taxes, le total et le numéro.

Réutilise le stockage privé et les outils PDF existants. N'ajoute une dépendance que si nécessaire et compatible.

Interdis l'accès public direct au PDF.

Un utilisateur ne peut télécharger que ses documents autorisés.

## 9. REPRISE APRÈS ÉCHEC

Teste et implémente les cas :

- Erreur avant réservation.
- Erreur après réservation.
- Erreur pendant la génération.
- Fichier généré mais finalisation interrompue.
- Job relancé.
- Requête répétée.
- Deux opérations concurrentes.

Une reprise ne doit jamais créer un deuxième numéro pour la même opération.

Un numéro réservé n'est jamais réutilisé.

Les données figées ne sont jamais recalculées arbitrairement pendant une reprise.

Utilise une clé de stockage déterministe liée au UUID du document selon le schéma.

## 11. TESTS DÉTAILLÉS ARRANGE / ACT / ASSERT

Pour chaque test, prépare les données, exécute l'action et vérifie les résultats HTTP, SQL, fichiers et audits.

### T19-01 — Facture valide

Arrange : propriétaire A, abonnement type 1, échéance type 2 de 3 000 DA, RULE applicable, compteur valide et identités fiscales de test validées.

Act : créer puis émettre la facture en utilisant les paramètres fiscaux de la fixture validée.

Assert : facture INVOICE, liens corrects, lignes et totaux cohérents, numéro unique, statut ISSUED, PDF privé existant et audit.

### T19-02 — Échéance étrangère

Arrange : propriétaires A et B, échéance de B.

Act : demander une facture de A utilisant l'échéance de B.

Assert : refus, aucune facture, aucun numéro consommé.

### T19-03 — Règle invalide

Arrange : RULE DRAFT ou hors période.

Act : tenter l'émission.

Assert : refus et aucune émission.

### T19-04 — Calculs

Arrange : plusieurs lignes avec paramètres fiscaux de test explicitement définis.

Act : calculer le document.

Assert : montants décimaux exacts, total HT + taxes = TTC, somme des lignes égale à l'en-tête.

### T19-05 — Numérotation

Arrange : compteur facture initialisé.

Act : émettre deux factures différentes.

Assert : deux numéros distincts, bon type et bon exercice, aucune collision.

### T19-06 — Retry

Arrange : opération émise.

Act : rejouer exactement la même création.

Assert : même facture, même UUID, même numéro, aucune ligne ni intention dupliquée.

### T19-07 — Crash après réservation

Arrange : provoquer un échec contrôlé entre PREPARING et génération PDF.

Act : reprendre l'opération.

Assert : même numéro, même document, finalisation correcte, absence de doublon.

### T19-08 — Fichier indisponible

Arrange : simuler un échec de stockage.

Act : générer le document.

Assert : pas de faux ISSUED, erreur traçable, reprise possible.

### T19-09 — Immutabilité

Arrange : facture ISSUED.

Act : tenter de modifier ses montants, lignes, identités ou son numéro.

Assert : refus et valeurs historiques inchangées.

### T19-10 — Changement de profil

Arrange : facture ISSUED avec snapshots.

Act : modifier le profil actuel du propriétaire dans la fixture.

Assert : snapshots et PDF de la facture inchangés.

### T19-11 — Téléchargement interdit

Arrange : facture de B.

Act : utilisateur A demande son PDF.

Assert : accès refusé, aucun octet du fichier exposé.

### T19-12 — Concurrence

Arrange : deux processus/connexions MySQL indépendants.

Act : tenter d'émettre simultanément une même opération logique et des opérations distinctes.

Assert : idempotence pour la même opération, numéros uniques pour les opérations distinctes.

Complète avec :

- Statuts et transitions.
- FK composites.
- Mauvais compteur.
- Ligne absente.
- Taxe invalide.
- Date incorrecte.
- Permissions.
- Audit.
- Média altéré.
- Intention de transmission.
- Isolation des BDD boutiques.
- Cas de sécurité HTTP.

N'utilise pas uniquement des mocks pour valider les contraintes MySQL ou l'existence du PDF.

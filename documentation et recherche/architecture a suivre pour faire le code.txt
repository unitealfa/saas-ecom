# Architecture Laravel du projet SaaS multi-tenant

## 1. Objectif général

Avant de commencer à développer les fonctionnalités, il faut organiser le projet Laravel de manière propre.

L’idée est de :

- séparer clairement la partie **centrale** de la plateforme ;
- séparer clairement la partie **boutique / tenant** ;
- éviter de mettre toute la logique dans les Controllers ;
- utiliser une architecture proche du principe **MVC** ;
- séparer la validation, la logique métier, les données et l’accès à la base de données ;
- garder un code simple à maintenir lorsque le projet devient grand.

Le projet utilise donc Laravel avec une organisation personnalisée autour de :

```text
Models
Controllers
Requests
Services
DTO
Migrations
Seeders
Routes
```

---

# 2. Séparer Central et Tenant

Le projet possède deux types de données.

## Central

La base centrale contient les informations appartenant à la plateforme.

Exemples :

```text
users
tenants
plans
subscriptions
countries
platform_roles
platform_permissions
```

## Tenant

Chaque boutique possède sa propre base de données.

Exemples :

```text
products
product_variants
orders
order_items
customers
stock_movements
delivery_rates
```

Il faut donc retrouver cette séparation directement dans le code.

# 3. Organisation des Models

Dans :

```text
app/Models/
```

créer deux dossiers :

```text
app/
└── Models/
    ├── Central/
    └── Tenant/
```

Par exemple :

```text
app/
└── Models/
    ├── Central/
    │   ├── User.php
    │   ├── Tenant.php
    │   ├── Plan.php
    │   └── Subscription.php
    │
    └── Tenant/
        ├── Product.php
        ├── ProductVariant.php
        ├── Order.php
        └── Customer.php
```

Donc :

```text
User
```

appartient à la base centrale.

Alors que :

```text
Product
```

appartient à la base de données de la boutique.

Il ne faut pas mettre tous les Models directement dans :

```text
app/Models/
```

sans séparation.

# 4. Organisation des migrations

Il faut appliquer exactement la même logique pour les migrations.

Au lieu d'avoir toutes les migrations dans le même dossier :

```text
database/migrations/
```

on peut organiser :

```text
database/
└── migrations/
    ├── central/
    └── tenant/
```

Exemple :

```text
database/
└── migrations/
    ├── central/
    │   ├── create_users_table.php
    │   ├── create_tenants_table.php
    │   ├── create_plans_table.php
    │   └── create_subscriptions_table.php
    │
    └── tenant/
        ├── create_products_table.php
        ├── create_product_variants_table.php
        ├── create_orders_table.php
        └── create_order_items_table.php
```

Les migrations `central` servent uniquement à créer les tables de la base centrale.

Les migrations `tenant` servent uniquement à créer les tables présentes dans chaque boutique.

---

# 5. À quoi sert une migration ?

Une migration permet de décrire la structure d'une table.

Par exemple :

```php
Schema::create('products', function (Blueprint $table) {
    $table->id();
    $table->uuid('uuid')->unique();
    $table->string('name');
    $table->decimal('price', 10, 2);
    $table->timestamps();
});
```

Laravel comprend alors :

```text
Si la table products n'existe pas,
crée-la avec ces colonnes.
```

Une migration représente donc le **schéma de la base de données**.

C'est comparable à la définition des schemas/models que l'on peut retrouver dans d'autres frameworks comme Node.js / Express.

# 6. Organisation des Seeders

Même principe pour les seeders.

Créer :

```text
database/
└── seeders/
    ├── Central/
    └── Tenant/
```

Par exemple :

```text
database/
└── seeders/
    ├── Central/
    │   ├── CountrySeeder.php
    │   ├── RoleSeeder.php
    │   └── PlanSeeder.php
    │
    └── Tenant/
        ├── RoleSeeder.php
        ├── SettingSeeder.php
        └── DefaultCategorySeeder.php
```

L'intérêt est de pouvoir exécuter séparément :

```text
les seeders Central
```

et :

```text
les seeders Tenant
```

Quand une nouvelle boutique est créée, Laravel peut :

```text
1. créer la base de données du tenant
2. exécuter les migrations tenant
3. exécuter les seeders tenant
```

Donc une nouvelle boutique reçoit automatiquement sa structure et ses données par défaut.

# 7. Organisation des Controllers

Même principe dans les Controllers.

Dans :

```text
app/Http/Controllers/
```

avoir :

```text
app/
└── Http/
    └── Controllers/
        ├── Central/
        └── Tenant/
```

Exemple :

```text
app/
└── Http/
    └── Controllers/
        ├── Central/
        │   ├── UserController.php
        │   ├── TenantController.php
        │   └── PlanController.php
        │
        └── Tenant/
            ├── ProductController.php
            ├── OrderController.php
            └── CustomerController.php
```

Le principe est simple :

```text
Controller Central
→ travaille avec la plateforme centrale

Controller Tenant
→ travaille avec une boutique
```

# 8. Le rôle du Controller

Le Controller ne doit pas contenir toute la logique métier.

Son rôle principal est :

```text
1. recevoir la requête HTTP
2. récupérer les données validées
3. appeler le Service
4. retourner la réponse
```

Par exemple :

```php
public function store(
    StoreProductRequest $request,
    ProductService $productService
) {
    $product = $productService->create(
        ProductData::fromRequest($request)
    );

    return response()->json($product, 201);
}
```

Le Controller doit rester relativement petit.

Il ne faut pas faire :

```text
validation
+ vérifications métier
+ création produit
+ stock
+ logs
+ notifications
+ calculs
```

directement dans le Controller.

---

# 9. Validation avec les Form Requests

Les données envoyées par le frontend doivent être validées avant d'être utilisées.

Par exemple :

```text
name
first_name
last_name
email
phone
price
```

Il faut utiliser les **Form Requests Laravel**.

Exemple :

```text
app/
└── Http/
    └── Requests/
        ├── Central/
        └── Tenant/
```

Puis :

```text
app/Http/Requests/Tenant/StoreProductRequest.php
```

Exemple :

```php
class StoreProductRequest extends FormRequest
{
    public function rules(): array
    {
        return [
            'name' => ['required', 'string', 'max:255'],
            'price' => ['required', 'numeric', 'min:0'],
        ];
    }
}
```

Le Request sert uniquement à vérifier les données reçues.

Il ne doit pas contenir la logique métier principale.

---

# 10. Utiliser des Services

La logique métier doit être placée dans des Services.

Créer par exemple :

```text
app/
└── Services/
    ├── Central/
    └── Tenant/
```

Exemple :

```text
app/Services/Tenant/ProductService.php
```

```php
class ProductService
{
    public function create(ProductData $data): Product
    {
        return Product::create([
            'name' => $data->name,
            'price' => $data->price,
        ]);
    }
}
```

Le Service peut gérer :

```text
vérifications métier
création
modification
calculs
transactions
appels à plusieurs Models
stock
commandes
abonnements
etc.
```

Donc :

```text
Controller
→ reçoit la demande

Service
→ exécute le travail
```

---

# 11. Utiliser des DTO

DTO signifie :

```text
Data Transfer Object
```

Son rôle est d'avoir une structure de données claire entre les différentes parties de l'application.

Par exemple le frontend peut envoyer :

```text
firstName
lastName
```

alors que la base contient :

```text
first_name
last_name
```

Sans règle claire, un développeur peut utiliser :

```text
fname
lname
firstName
first_name
```

et cela devient rapidement désordonné.

Le DTO permet de définir une forme unique.

Par exemple :

```php
class UserData
{
    public function __construct(
        public string $firstName,
        public string $lastName,
        public string $email,
    ) {}
}
```

Puis :

```php
$userData = new UserData(
    firstName: $request->first_name,
    lastName: $request->last_name,
    email: $request->email,
);
```

Le Service reçoit alors toujours la même structure.

# 12. Flux complet recommandé

Lorsqu'une requête arrive depuis le frontend :

```text
Frontend
   ↓
Route
   ↓
Form Request
   ↓
Controller
   ↓
DTO
   ↓
Service
   ↓
Model
   ↓
Base de données
```

Puis dans le sens retour :

```text
Base de données
   ↓
Model
   ↓
Service
   ↓
Controller
   ↓
Response JSON
   ↓
Frontend
```

Exemple concret :

```text
Le marchand clique sur "Créer un produit"
```

Le frontend envoie :

```http
POST /api/products
```

avec :

```json
{
    "name": "Chaussure Nike",
    "price": 9500
}
```

Laravel passe par :

```text
Route
↓
StoreProductRequest
↓
ProductController
↓
ProductData
↓
ProductService
↓
Product Model
↓
BDD Tenant
```

```text
DTO/Tenant

```

Par exemple :

# 17. Principe à retenir

L'objectif n'est pas d'avoir une architecture extrêmement compliquée.

L'objectif est :

```text
simple
+
claire
+
séparée
+
maintenable
```

Il ne faut donc pas essayer d'appliquer tous les patterns possibles.

On reste sur :

```text
MVC
+
Form Requests
+
Services
+
DTO
+
séparation Central / Tenant
```

avec quelques principes SOLID lorsque cela apporte réellement quelque chose.

La règle principale est :

```text
Une classe = une responsabilité principale.
```

Par exemple :

```text
Request
→ validation

Controller
→ entrée / sortie HTTP

DTO
→ transport des données

Service
→ logique métier

Model
→ données / relations BDD

Migration
→ structure BDD

Seeder
→ données initiales
```

C'est cette architecture qui permet ensuite de commencer le développement proprement sans mélanger toute la logique du SaaS.

# 18. Organisation Aydra confirmée le 10 octobre 2026

Cette décision précise les exemples précédents et prévaut pour les prochaines interventions. Le dossier réel des DTO est `app/DTOs`, au pluriel. La séparation comporte désormais trois contextes fonctionnels, mais toujours deux types de bases de données :

| Contexte | Responsabilité | Base utilisée |
|---|---|---|
| Central | Comptes de la plateforme, administration et registre des boutiques | Centrale |
| Tenant | Gestion interne d'une boutique | Base de cette boutique |
| Storefront | Pages et accès publics d'une boutique | Base de cette boutique, après initialisation Tenancy |

Les Models restent dans `app/Models/Central` et `app/Models/Tenant`. Storefront réutilise les Models tenant ; il ne crée ni troisième BDD ni copie des données. Les Controllers, Requests, Services, DTOs, Policies et autres composants spécifiques sont rangés dans leur contexte. On ne crée les dossiers et fichiers qu'au moment où ils sont nécessaires.

| Composant existant | Emplacement |
|---|---|
| Actions d'authentification Fortify centrales | `app/Actions/Central/Auth/Fortify` |
| Actions Livewire centrales | `app/Livewire/Central/Auth/Actions` |
| Middlewares propres à un contexte | `app/Http/Middleware/Central` ou `app/Http/Middleware/Tenant` |
| Contrôleur d'accueil public de boutique | `app/Http/Controllers/Storefront/StorefrontController.php` |
| Pages du starter kit réservées au central | `resources/views/central/pages/auth`, `resources/views/central/pages/settings` |
| Pages Livewire du dashboard et des utilisateurs centraux | `resources/views/central/pages` |
| Layouts centraux | `resources/views/central/layouts` |
| Composants et fragments propres aux comptes centraux | `resources/views/central/components`, `resources/views/central/partials` |
| Factories | `database/factories/Central`, `database/factories/Tenant` |
| Tests | `tests/Central`, `tests/Tenant` ; les futurs tests publics spécifiques vont dans `tests/Storefront` |
| Routes centrales et réglages | `routes/central.php`, `routes/central/settings.php` |
| Routes internes tenant | `routes/tenant.php` |
| Routes publiques de boutique | `routes/storefront.php`, inclus dans le groupe de middlewares tenant |
| Migrations et seeders | `database/migrations/central`, `database/migrations/tenant`, `database/seeders/Central`, `database/seeders/Tenant` |

`config/livewire.php` associe les alias historiques `pages::` et `layouts::` aux dossiers centraux ci-dessus ; ces alias sont réservés au central. Les alias explicites `central::`, `tenant::` et `storefront::` associent les vues à leur contexte et permettent de générer directement les prochains composants à leur emplacement. Une future page Tenant ou Storefront choisit explicitement un layout de son contexte, sans employer par défaut le layout central. Les noms techniques des fichiers Livewire existants et les noms de routes sont conservés ; les références affectées par un déplacement sont mises à jour. Lors de la création d'un nouveau dossier de tests de contexte, sa découverte doit aussi être ajoutée dans `phpunit.xml` et `tests/Pest.php` selon le besoin.

Les classes d'infrastructure communes, les traits partagés, le pivot polymorphe `PermissionAssignment`, `SchemaBlueprint`, les providers, les composants visuels réutilisables et l'orchestration des tests/seeders restent partagés. Les points d'entrée `App\Models\User` et `App\Models\Tenant` conservent la compatibilité avec les implémentations centrales documentées. `app/Models/Test.php` reste un exemple technique sans contexte métier, conformément à la réponse de l'utilisateur.

Avant chaque opération sur un fichier, vérifier cette organisation et l'absence d'un équivalent. Ne pas ajouter d'emojis ; préserver uniquement les caractères techniques des frameworks. Après un déplacement, vérifier les références, la configuration chargée, les routes et les tests concernés sans changer les données existantes.

# 19. Préparation Tenant confirmée le 11 octobre 2026

Les dossiers Tenant accompagnent leurs équivalents Central. Les fichiers ci-dessous constituent une base pour la suite ; aucune nouvelle route d'authentification, de dashboard ou de profil boutique n'est enregistrée. Le développement fonctionnel des boutiques reste reporté après celui de la plateforme centrale.

| Élément préparé | Emplacement |
|---|---|
| Layout interne et barre latérale | `resources/views/tenant/layouts/app.blade.php`, `resources/views/tenant/layouts/app/sidebar.blade.php` |
| Layout d'authentification | `resources/views/tenant/layouts/auth.blade.php`, `resources/views/tenant/layouts/auth/simple.blade.php` |
| Vue de connexion | `resources/views/tenant/pages/auth/login.blade.php` |
| Vues d'accueil et de profil | `resources/views/tenant/pages/admin/dashboard/dashboard.blade.php`, `resources/views/tenant/pages/settings/profile.blade.php` |
| Présentation du compte et message de préparation | `resources/views/tenant/components/account-summary.blade.php`, `resources/views/tenant/partials/preparation-notice.blade.php` |
| Coordination HTTP du futur accueil | `app/Http/Controllers/Tenant/Admin/Dashboard/DashboardController.php` |
| Lecture des données de l'accueil | `app/Services/Tenant/Dashboard/Dashboard.php` |
| Données transmises aux vues | `app/DTOs/Tenant/Dashboard/DashboardData.php` |
| Tests isolés de cette préparation | `tests/Tenant/Feature/Dashboard/DashboardControllerTest.php` |

Le contrôleur préparé utilise exclusivement le compte du guard `tenant`. Le service exige un contexte boutique initialisé, un compte et une appartenance actifs, une invitation acceptée (`joined_at`) et un e-mail vérifié. Il lit le seul profil `shop` local et vérifie sa référence `tenant_uuid`. Le DTO transmet uniquement le nom de la boutique et celui du compte ; les vues n'effectuent aucune requête SQL. Les tests enregistrent leur route uniquement dans l'application de test et utilisent des bases MySQL temporaires isolées.

La vue de connexion reste sans formulaire tant qu'une action tenant explicite n'est pas transmise dans `loginAction`. Son éventuel lien de récupération est fourni séparément dans `passwordRequestUrl` ; elle ne réutilise aucune route Fortify centrale et ne propose pas d'inscription publique boutique. Ces contrats visuels ne configurent ni Fortify tenant, ni un flux d'invitation, ni l'envoi de messages.

Les layouts utilisent explicitement `tenant::`, les composants communs compatibles et le lien relatif existant `tenant.home` vers la vitrine. Les menus d'administration, rôles, passkeys et paramètres centraux ne sont pas copiés. Les dossiers réservés aux futures Actions, Notifications, Requests, Policies, actions Livewire, routes et tests unitaires Tenant restent disponibles avec leurs marqueurs `.gitkeep` lorsqu'aucun fichier utile n'est encore nécessaire. Les modèles, migrations, factories et seeders Tenant existants sont réutilisés.

# 20. Administration centrale confirmée le 11 octobre 2026

Le fragment resources/views/partials/head.blade.php reste commun : métadonnées HTML, assets Vite et apparence Flux, sans requête ni compte central. Les layouts Central et Tenant le réutilisent ; les autres fragments propres aux comptes restent dans leur contexte.

Les Controllers et Form Requests Central coordonnent les formulaires de rôles, comptes et boutiques. Les DTOs de app/DTOs/Central transportent les données vers RoleManager, UserManagementService et TenantCreator ; les vues vont dans resources/views/central/pages/{roles,tenants} et resources/views/central/pages/admin/users. Les Policies protègent aussi les URL et les actions serveur.

Les rôles, permissions et attributions utilisent exclusivement Spatie Laravel Permission et ses cinq tables existantes. Role et Permission héritent des modèles Spatie ; les extensions séparées conservent UUID, durées, dates d’attribution, signatures et versions. AuthorizationMutation verrouille le rôle root protégé puis les rôles/comptes concernés, contrôle les noms/compositions identiques, durées de 1 à 9 999 jours et recoupements. UserManagementService utilise syncRoles de Spatie enrichi par le contrat daté existant ; conserver un rôle conserve sa date. Aucun système d’autorisation parallèle n’est créé.

Le Super Admin crée/modifie les rôles de gestion des utilisateurs ; les rôles système restent protégés. Son rôle n’est pas attribuable depuis ces formulaires. Un administrateur délégué possédant saas.staff.invite et saas.users.roles.assign peut gérer le personnel et déléguer uniquement des droits qu’il possède encore. Les dates restent contrôlées ; admin_restrictions est retiré de la cible (instructionn.txt, §24). Les permissions sont regroupées par module (comptes commerçants, personnel SaaS, pays). Un droit de gestion actif permet aussi la consultation du module dans sa portée ; les protections techniques et dates restent contrôlées, sans permission ajoutée aux pivots Spatie. Inviter le personnel (saas.staff.invite) et le modifier (saas.staff.update) sont distincts. Les nouvelles actions de suspension, réactivation et suppression sont séparément autorisées. Les comptes créés par l’administration sont invités à choisir leur mot de passe par le broker central de Fortify, puis se connecter ; le lien valide confirme également leur adresse e-mail. Après la correction confirmée le 11 octobre, AccountMailDelivery utilise notifyNow de Laravel après commit : l’invitation part directement, sans worker. AccountInvitation reste compatible avec les anciens jobs chiffrés. Une panne SMTP conserve le compte, affiche un avertissement et permet un renvoi autorisé depuis sa fiche ; aucun mot de passe partagé ni secret n’est journalisé.

Le plan gratuit par défaut, code free, possède la fonctionnalité shops : quota de quantité à portée propriétaire, période totale, maximum deux boutiques. FreePlanSeeder crée uniquement les référentiels ; DefaultSubscription attribue le type 1 actif sans facture fictive. Les abonnements payants existants sont préservés. Les offres utilisées sont versionnées.

TenantCreator verrouille le propriétaire, vérifie creation_key et creation_hash avant le quota et compte ses boutiques non archivées, préparations/échecs compris. Les DTOs, Requests et Services centraux plats mélangent identité, pays, rôles, abonnements et provisionnement. Les Controllers administratifs sont regroupés dans Central/Admin/{Users,Roles,Countries,Tenants}. Les Services Users déjà organisés ne bougent pas. Auth regroupe les Actions Fortify, invitations, réponse d’inscription, middleware et action Livewire de déconnexion. Authorization porte les contrôles communs aux modules ; Roles porte le catalogue et la gestion des rôles. Plans et Subscriptions restent séparés. Tenant conserve ses seuls modules réellement préparés : Shop, Dashboard, Users et Diagnostics. Les enums tenant d’utilisateur rejoignent Tenant/Users, sans changer leurs valeurs.

Les Models/Policies et factories sont conservés dans les dossiers Central/Tenant déjà documentés, comme dans la structure cible demandée. Les Models sont aussi des contrats de morph map, d’authentification et de sérialisation ; aucun déplacement artificiel n’est nécessaire. Les seeders conservent leurs chemins de contexte et commandes existantes ; les seeders de jeux d’essai orchestrent plusieurs modules. Les jobs sérialisables, Providers, bootstrappers Tenancy, traits partagés, SchemaBlueprint, PermissionAssignment et modèles de compatibilité restent à leur emplacement documenté. Les enums réellement partagés ActivityOriginEnum/VerificationStatusEnum ne sont pas dupliqués. Le modèle Test reste un exemple technique sans table métier.

Les layouts, composants communs et alias Livewire existants restent compatibles. Les pages d’authentification et de réglages sont déjà groupées ; settings reste le module du profil et des réglages personnels, sans nouvelle copie Owner/Profile. Storefront reste un contexte distinct sous app/Http/Controllers/Storefront et routes/storefront.php, inclus dans la protection Tenant. Les tests gardent tests/{Central,Tenant}/{Feature,Unit,...}, leur découverte Pest/PHPUnit et leurs classes de base ; les tests transversaux restent transversaux.

## 25.3 Routes et références

routes/central.php reste le point d’entrée chargé par routes/web.php sur les domaines centraux. Les routes d’administration vont dans routes/central/admin.php puis ses fichiers admin/{users,roles,countries,tenants}.php, inclus à l’intérieur du même groupe auth:central, verified et compte actif. Les routes de diagnostic centrales vont dans routes/central/diagnostics.php avec la protection locale existante. Les routes Fortify restent fournies par le package : ne pas créer de routes/auth.php concurrentes. settings.php et les groupes Tenant/Storefront conservent leurs contrats, URL, noms, middlewares et ordre relatif. Seules les références de classes et vues déplacées changent.

Mettre à jour namespaces, imports, références pleinement qualifiées, vues/composants, tests, Providers et configurations concernés. Préserver les alias morph et les classes des jobs déjà sérialisés. Régénérer l’autoload Composer sans scripts ; effacer seulement les vues compilées si nécessaire, sans optimize:clear ni effacement du cache de BDD. Les migrations et fichiers de verrouillage doivent être identiques aux empreintes prises avant cette refactorisation.

# 26. Module 02 — personnel SaaS

Développer uniquement le personnel de la plateforme centrale, avec le guard central et les modèles/pivots Spatie existants. Ne pas activer les fonctionnalités Tenant. Les rôles système, le Super Admin et les durées restent protégés ; aucune table d’autorisation parallèle. La question des permissions directes dans l’interface doit être résolue explicitement avant d’implémenter leur attribution.

Emplacements du module, cohérents avec instructionn.txt et le classement du §25 : Controllers dans app/Http/Controllers/Central/Admin/Staff ; Form Requests dans app/Http/Requests/Central/Users ; StaffManagementService et StaffInvitationService dans app/Services/Central/Users ; CentralRoleAssignmentService et CentralPermissionResolver dans app/Services/Central/Authorization ; Policy existante app/Policies/Central/UserPolicy.php ; vues dans resources/views/central/pages/admin/staff ; routes dans routes/central/admin/staff.php, inclus par routes/central/admin.php ; tests dans tests/Central/Feature/Admin/Staff. Réutiliser UserData/UserProfileData et les services de comptes/invitation existants, sans recopier la chaîne Fortify. Une permission de gestion ouvre la consultation nécessaire au module tout en conservant son contrôle propre pour la mutation.

L’utilisateur autorise les tests MySQL temporaires pour les Modules 01 et 02 et l’application de la migration/seeder manquants au central, sans réinitialisation des données. Le Module 01 doit être validé avant de commencer le Module 02. Les résultats et l’état réel sont consignés dans le suivi.

Réalisation disponible : liste Livewire central::pages.admin.staff.index et layout central ; invitations/édition/états via StaffController et services de comptes existants ; rôles via StaffRoleController et CentralRoleAssignmentService ; inspection des droits via StaffPermissionController et CentralPermissionResolver. Les Form Requests Staff réutilisent les validations Users et leurs DTOs, en conservant les autorisations propres aux actions Staff. Les champs professionnels, mots de passe, statuts et rôles ne sont pas librement modifiables par le formulaire d’identité du personnel.

La liste du personnel suit la définition existante isStaff : présence d’un rôle central, même si ses droits sont expirés. Retirer tous les rôles ne supprime pas le compte ; il revient à la liste générale des utilisateurs. Les anciens codes staff.restore/delete deviennent staff.activate/archive par le catalogue, en conservant leur ligne, UUID, pivots et signature. Les rôles existants ne reçoivent pas automatiquement de nouvelles permissions.

Pour déléguer, ownsPermission relit la permission native Spatie à l’heure courante ; allows peut continuer de déduire une consultation utile sans permettre de transmettre ce droit. Pour renouveler, vérifier saas.staff.assignments.renew et la possession des droits du rôle, sans imposer saas.users.roles.assign pour ce rôle déjà attribué. assigned_at est produit par le serveur ; expected_assigned_at compare seulement la version affichée, sans définir le nouveau début. Refuser une attribution absente ou une version obsolète ; éviter une seconde mutation si le début vaut déjà la seconde courante. Le motif, les dates et le UUID du rôle sont audités par Activitylog ; le remplacement journalise aussi les attributions avant/après. Le resolver expose les droits natifs Spatie et leurs échéances ; il ne remplace aucune Policy et ne décide aucune mutation.

Contrôles communs aux Modules 01 et 02, vérifiés le 13 octobre 2026 : UserPolicy.resendInvitation délègue à resendStaffInvitation pour un compte personnel, y compris sur l’ancienne route Utilisateurs. Celle-ci exige le droit saas.staff.invite.resend, un destinataire actif non vérifié et les protections existantes contre la gestion d’un compte plus privilégié. Le Controller, le service sous verrou et le bouton appliquent cette capacité ; le renvoi au commerçant conserve ses règles existantes. mayManageStaff permet la modification de sa propre identité si le compte est encore actif et possède le droit de modification requis, même si un autre droit a expiré. Les Policies interdisent toujours l’auto-attribution de rôles et les changements de son propre état ; aucun droit expiré n’est renouvelé par une modification de profil.

# 27. Instances PHP et injection des dépendances

Demande confirmée le 13 octobre 2026 : vérifier chaque classe et conserver la bonne convention d’utilisation de `$this` pour la suite. `$this` représente l’objet courant ; il permet de réutiliser ses propriétés et méthodes. Son emploi seul ne garantit aucun gain de temps ni de mémoire.

- Dans une méthode d’instance, accéder à ses membres avec `$this->property` et `$this->method()`. Les paramètres, variables locales et autres objets restent accessibles avec leur propre variable. Une propriété promue dans le constructeur est déjà créée par PHP ; aucune affectation manuelle supplémentaire n’est nécessaire.
- Si un service est utilisé par plusieurs méthodes de la même classe, préférer l’injection au constructeur avec une propriété typée, généralement private, puis réutiliser cette propriété. Ne pas cumuler son injection au constructeur et sa réinjection dans les méthodes. L’injection de méthode Laravel reste adaptée à un besoin propre à une action ; les Form Requests et les modèles liés aux routes conservent leur cycle normal.
- Les DTOs transportent des données. Les enums, classes sans état, hooks statiques Eloquent, facades Laravel et appels self::/static::/parent:: conservent leur fonctionnement. Ne pas ajouter artificiellement `$this`, un constructeur ou une dépendance pour rendre tous les fichiers identiques. `$this` n’est pas disponible dans une méthode ou fermeture statique.
- Livewire : respecter sa construction et son hydratation ; ne pas remplacer son constructeur par une injection métier. Utiliser l’injection dans les actions ou dans boot lorsque la version installée le permet ; un service conservé par la composante doit rester dans une propriété non publique et être réinitialisé pour chaque requête concernée. Les résolutions app() existantes dans les propriétés calculées ne sont pas automatiquement des erreurs.
- Jobs : conserver les données sérialisables dans le constructeur et résoudre les services dans handle. Providers : `$this->app` est le conteneur existant. Les résolutions de services liées au changement de contexte Spatie/Tenancy et après commit restent compatibles ; ne pas les remplacer aveuglément par un service conservant un ancien contexte.
- Ne pas transformer tous les services en singletons ni conserver un utilisateur, tenant, modèle, Builder ou autorisation mutable dans une propriété pour gagner du temps. Respecter le cycle de la requête/du job et l’isolation des boutiques ; le contexte et les droits actuels doivent être relus lorsque nécessaire. Toute affirmation de performance exige une mesure représentative.

Exemple existant : UserApprovalService reçoit AuthorizationMutation dans son constructeur et utilise `$this->mutations->run(...)`. UserController réutilise désormais `$this->userServices` pour ses sept opérations de service, au lieu de résoudre à nouveau le même service dans cinq méthodes. Règles métier, routes et autorisations préservées. L’inventaire individuel et les limites des contrôles sont consignés dans l’entrée du suivi du 13 octobre 2026 relative aux instances et dépendances.

Références vérifiées pour les versions installées : Laravel 13, injection dans les [Controllers](https://laravel.com/docs/13.x/controllers#dependency-injection-and-controllers) et [conteneur](https://laravel.com/docs/13.x/container) ; Livewire 4, [injection dans les actions](https://livewire.laravel.com/docs/4.x/actions#dependency-injection). Les APIs installées et les contraintes de sérialisation/hydratation priment sur une généralisation de cet exemple.

# 28. Photos de profil facultatives

Aucun équivalent de ces composants n’existe lors de la reconnaissance.

La photo personnelle est indépendante des permissions d’administration : un compte central actif peut modifier sa propre photo ; consulter celle d’un autre compte exige le droit de consultation existant. Le serveur choisit le parent et la collection ; aucun ID, chemin ou disque de stockage n’est fourni librement par le formulaire. Les fichiers sont conservés sur le disque local privé et servis sous autorisation et signature Laravel, conformément au §7.6 du schéma ; URL relative pour préserver l’hôte et le port courants, réponse privée sans cache. Formats raster validés, limite technique de poids et dimensions, noms générés, aucun SVG utilisateur. Remplacer/retirer verrouille le véritable utilisateur, archive la référence précédente puis supprime le fichier devenu inutile après commit ; une transaction échouée conserve la photo précédente et nettoie le nouveau fichier. Les mutations sont auditées avec Activitylog sans exposer les chemins ni le contenu des photos.

La relation et l’avatar commun sont préparés dans les modèles Tenant sans ouvrir ses routes de connexion ou de dashboard. Le getter Tenant renvoie l’avatar commun tant que sa route de photo n’est pas activée. Les tests MySQL temporaires ciblés sont également autorisés pour cette demande, sans écriture dans les bases existantes. Ne pas présenter la préparation Tenant comme une interface de modification fonctionnelle ; les résultats sont consignés dans le suivi.

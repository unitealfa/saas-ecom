# Workers Docker locaux Aydra

Périmètre : Windows/Herd, MySQL local, Docker Desktop Linux. Aucun changement à la production. Une image de runtime PHP 8.5 sans code Aydra, sans vendor, sans .env, ni documents. Docker construit et stocke cette image sur le poste ; Docker Desktop exécute quatre conteneurs. Aucun compte ni dépôt Docker Hub, aucun push d’image. Les images publiques de base PHP et Composer sont téléchargées à la première construction. Le projet est monté en lecture seule ; storage est partagé en lecture-écriture, vendor Linux est un volume distinct par projet et version de composer.lock/image ; bootstrap/cache est temporaire par conteneur.

## Installation initiale

1. Vérifier PHP 8.5, Docker Desktop en mode Linux et Compose V2. Arrêter les tâches historiques (`php artisan aydra:local-queue stop`) lorsqu'aucun travail critique n'est en cours ; arrêter aussi tout worker ou Scheduler lancé manuellement. Ne pas lancer Docker sur une base de production, ni exposer MySQL à Internet.
2. Docker Desktop doit être lancé en mode conteneurs Linux avec le contexte local par défaut ou desktop-linux. Aucun login Docker Hub requis pour un usage normal des images publiques ; un accès Internet est nécessaire à la première construction. L’installateur Python ajoute uniquement les fichiers du projet, pas Docker Desktop lui-même.
3. L’image est construite automatiquement par `aydra:docker-workers check` ou `start`, avec un tag local calculé à partir du Dockerfile. Si le tag existe, il est réutilisé. Le contexte de build se limite à deployment/docker et exclut tout sauf le Dockerfile. Git contient les recettes, jamais les images ni les volumes.
4. Renseigner dans le .env Windows existant : `AYDRA_LOCAL_WORKERS=docker`, `QUEUE_ACCOUNT_MAIL_CONNECTION=database`. Conserver `APP_ENV=local`, `DB_CONNECTION=mysql`, `DB_HOST=127.0.0.1`, le nom et les identifiants MySQL locaux existants, `QUEUE_CONNECTION=database`, `DB_QUEUE_CONNECTION=mysql`, `CACHE_STORE=database`, `FILESYSTEM_DISK=local`. Ne pas changer APP_KEY. DB_URL et DB_SOCKET doivent être absents/vides et le SSL MySQL distant n'est pas pris en charge par ce mode. Les conteneurs utilisent host.docker.internal ; leur accès MySQL doit être autorisé uniquement depuis le réseau Docker local, avec les droits existants sur la centrale et les bases boutique. Si refus MySQL, vérifier le compte utilisateur/hôte exact et le pare-feu ; aucune modification SQL automatique.
5. `php artisan config:clear` puis `php artisan aydra:docker-workers check`. Cette commande prépare les dépendances Linux et effectue une sonde sans consommer de jobs. Une dépendance Composer nécessite Internet lors du premier lancement ou d'un changement de lock. Le test de connexion centrale ne prouve pas le droit CREATE DATABASE pour une boutique.
6. `php artisan serve` (ou `composer dev` avec Herd). L’image locale absente est construite ; les conteneurs existants sont réutilisés si la configuration et le code n'ont pas changé. Aucun port Docker publié. Le serveur Artisan garde son comportement HTTP normal ; les domaines Aydra/Herd et APP_URL doivent rester cohérents. Le Scheduler se lance en même temps. `php artisan aydra:docker-workers status` ; `php artisan aydra:docker-workers logs` ; `php artisan aydra:docker-workers restart` après une modification de code pendant que les conteneurs tournent. `php artisan aydra:docker-workers stop` pour les arrêter ; Ctrl+C arrête le serveur HTTP, pas les workers. Ne pas arrêter au milieu d'une migration ou d'un envoi si évitable.

## Files et sécurité

- provisioning : central-provisioning / tenant-provisioning ; 3 essais, 300 s ; création, migrations, projection.
- documents : database / saas-documents ; 1 essai, 60 s ; documents et notifications SaaS.
- account-mail : database / default ; 3 essais, 60 s ; nouveaux listeners de comptes.
- scheduler : schedule:work ; un seul exemplaire. Aucun Redis ni Supervisor local requis. Les politiques de reprise existantes sont conservées ; Docker redémarre les processus, pas les jobs manuellement.
- Mail : MAIL_HOST local est traduit en host.docker.internal pour le worker. Le transport log est sans envoi réseau, mais certaines invitations tenant le refusent. Pour un vrai test de bout en bout utiliser un SMTP de test local (par exemple Mailpit séparé) et ne pas utiliser des adresses réelles. Le worker consomme les jobs existants dès démarrage, vérifier leur contenu et choisir une base de développement.
- APP_KEY et paramètres effectifs sont comparés entre hôte et conteneur, sans afficher les valeurs. Le code local est monté, jamais intégré au contexte de build ni publié. Les conteneurs ont accès aux secrets et documents locaux indispensables : ne jamais utiliser une image non fiable. Les logs peuvent contenir des informations privées, ne pas les publier.
- Les modifications de PHP sont détectées au prochain démarrage de serve ; si serve reste ouvert, lancer restart. Composer Linux est isolé de vendor Windows. Ne jamais lancer deux systèmes de supervision sur la même file/base. Ne pas partager une base de test avec production. Aucun reset, migration, purge ou seeder exécuté par l'installateur.

## Validation

Contrôles attendus : check, status (4 services actifs), test de création d'une boutique de développement, migration contrôlée sur boutique de test, invitation centrale et tenant via SMTP de test, envoi d'un document de test, vérifier le Scheduler et l'absence d'erreurs dans les logs. Les tests Pest existants ne démarrent pas Docker. Chaque conteneur effectue la sonde avant de commencer à traiter les jobs ; en cas de configuration modifiée, les anciens conteneurs peuvent refuser de redémarrer jusqu’à `restart`. Docker Desktop doit déjà être disponible ; le démarrage automatique concerne les conteneurs, pas le moteur Docker. Les tests de bout en bout restent à réaliser par l'utilisateur. Ne pas publier d’image pour ce chantier.

## Correctif de préparation Composer

Composer installe d'abord les paquets dans un répertoire temporaire Linux, puis les copie dans le volume dédié et génère l'autoloader depuis /app. Le volume est identifié aussi par le script d'installation et utilise nocopy, afin de ne jamais importer les dépendances Windows. Aucun ancien volume n'est supprimé. Les services exécutent la sonde avant leur commande et créent le marqueur de disponibilité. Ne pas effacer vendor Windows ni utiliser docker system prune pour ce dépannage.
